## 一、为什么要分成两轮

当前项目把正常业务、并发正确性和故障恢复写在了同一套代码中。例如发布博客同时包含参数校验、数据库事务、请求幂等、图片状态机和提交后文件删除。设计本身有价值，但第一次阅读时很难看清最基本的业务主线。

因此建议按两轮理解和实现：

1. **第一轮：正常流程版。** 明确假设 MySQL、Redis、网络、文件系统都正常，同一时刻也没有重复或并发请求；只讲用户做了什么、代码按什么顺序读写数据、最后返回什么。
2. **第二轮：数据与故障增强版。** 再取消这些理想假设，处理多步写入只成功一半、并发重复关系、数据库回滚、响应丢失、Redis 故障、文件删除失败、缓存不一致和进程崩溃。

> [!important] 分层表示学习和讲解顺序，不表示要破坏当前代码
> 当前项目已经存在的 `@Transactional`、唯一索引、行锁和幂等记录不需要删除。第一轮阅读时先把它们暂时遮住，只追踪正常业务主线；第二轮再逐一恢复并解释它们解决的具体失败场景。第一轮是教学用 Happy Path，不是可以直接上线的生产版本。

第一轮仍保留与故障无关的业务边界，例如必填参数、登录身份、对象归属、禁止关注自己和资源不存在；事务、唯一约束、并发幂等、影响行数裁决、缓存一致性和失败补偿统一进入第二轮。

## 二、第一轮：正常流程版

### 2.1 全域统一规则

#### 第一轮保留

1. 页面动作 → Controller → Service → Mapper → MySQL/Redis → 成功响应。
2. 必填参数校验、登录身份、对象归属和资源存在性判断。
3. 多步业务按正常顺序依次读写数据。
4. MySQL、Redis、短信和文件系统均成功返回。
5. 单个请求独立完成业务流程。

#### 第二轮增加

1. 数据库事务、回滚和影响行数裁决。
2. 唯一约束、锁、条件更新和并发幂等。
3. Redis 故障回源、缓存一致性和限流。
4. 网络响应丢失后的安全重试与状态对齐。
5. 文件、短信等外部资源的状态记录、补偿和重试。

基础调用链统一理解为：

```text
HTTP 请求
  → Controller 接收 DTO
  → Service 校验业务并编排流程
  → Mapper 读写 MySQL
  → 正常返回 Result
```

### 2.2 用户与身份域

#### 第一轮保留

- 发送验证码：校验手机号，生成验证码，保存到 Redis。
- 注册：校验验证码或账号密码，在 `tb_user` 创建用户。
- 登录：查询用户并校验凭据，在 Redis 保存登录 Token。
- 查询本人和修改资料：读取 `UserHolder` 中的当前用户，只更新允许修改的资料字段。
- 签到：用 Redis Bitmap 记录当天是否签到并统计连续天数。
- 密码不以明文保存，登录时验证用户提交的凭据。
- 修改资料只能修改当前登录用户，不能由请求体指定另一个用户。

#### 第二轮增加

- `account`、`phone` 数据库唯一约束与并发注册裁决。
- 账号创建和手机号绑定的事务或两阶段状态机。
- Redis Token 值与 TTL 的原子写入。
- 短信发送和验证码状态的一致性处理。
- Redis 不可用时的认证、登录和签到错误语义。

### 2.3 店铺域

#### 第一轮保留

- 用户点击店铺卡片或博客中的关联商户，页面自动取得 `shopId` 并调用 `GET /shop/{id}`。
- Service 根据 ID 查询 MySQL，返回店铺详情或 404。
- 用户选择分类时按 `typeId` 分页查询店铺。
- 用户允许定位后，通过 Redis GEO 查询 5km 内的附近店铺。
- 页面首次打开时，按 `sort` 查询店铺分类。
- 运营人员新增和更新店铺。

```text
用户点击店铺卡片
  → 前端从卡片/路由取得 shopId
  → GET /shop/{id}
  → Service 查询 MySQL
  ├─ 店铺存在：返回店铺详情
  └─ 店铺不存在：返回 404/“店铺不存在”
```

#### 第二轮增加

- 店铺详情 JSON 缓存和短 TTL 空值缓存。
- 热点店铺缓存重建锁、有界等待和随机 TTL。
- Redis 异常时回源 MySQL。
- 随机无效 ID 的参数校验与限流。
- 更新、删除的影响行数检查。
- 类型分页的稳定排序。
- 店铺写接口的管理员权限和请求 DTO。
- 新增、更新、删除后的详情缓存与 GEO 同步。
- 真实 MySQL、Redis 和 GEO 集成测试。

完整机制见 [4.5 店铺查询的缓存与故障增强](#45-店铺查询的缓存与故障增强)。

### 2.4 搜索域

#### 第一轮保留

- 一个搜索框对应“综合、店铺、笔记、用户”四种结果视图；“综合”是三个业务域的分组聚合，不是第四个 `SearchScope`。
- `GET /search?keyword=&scope=&current=&pageSize=` 是统一入口；`scope` 为空时按 `SHOP/BLOG/USER` 顺序召回全部域，明确传入 scope 时只调用所选 Tab。
- `GET /search/shops` 按店铺名称搜索，`GET /search/blogs` 按笔记标题或正文搜索，`GET /search/users` 只按公开昵称搜索。
- `SearchController` 只处理 HTTP 参数和响应包装；`DefaultUnifiedSearchService` 只做确定性选路与分组，不编写任何业务 SQL。
- `ShopSearchService`、`BlogSearchService`、`UserSearchService` 是平级的 `VerticalSearchService<T>`；各自的 MySQL 实现只负责本域。
- 三个 MySQL 搜索实现统一对关键词去除首尾空白、限制最多 64 个字符，并使用浅分页；页大小限制为 1～10。
- 空关键词返回空页；`%`、`_` 和反斜杠按普通字符转义，不把用户输入当作额外通配规则。
- 店铺和用户按 `id ASC` 稳定分页；笔记按 `create_time DESC, id DESC` 稳定分页。
- 店铺返回 `ShopSearchItemDTO`；笔记复用不含完整正文的 `BlogCardDTO`；用户只返回 `UserDTO(id/nickName/icon)`，账号、手机号和密码既不参与匹配也不进入 SELECT/响应。
- `BlogAssembler` 一次批量补齐整页笔记作者与点赞状态，不逐篇查询用户。
- `/shop/of/name` 仅作为旧页面兼容入口，共用同一 Service，不保留第二套 SQL。
- `SearchSuggestionService` 仍然只有合同，没有输入联想端点；Nuxt 已实现“综合｜店铺｜笔记｜用户”结果页和垂直域独立分页。

```text
用户输入“火锅”并点击搜索
  → GET /search?keyword=火锅
  → SearchController
  → DefaultUnifiedSearchService
       ├─ SHOP → tb_shop.name LIKE '%火锅%'
       ├─ BLOG → tb_blog.title/content LIKE '%火锅%'
       └─ USER → tb_user.nick_name LIKE '%火锅%'
  → 按 SHOP/BLOG/USER 分组返回
```

当前完成的是后端 MySQL 关键词基线、跨域分组接口和统一 Nuxt 结果页；输入提示、中文分词、相关度、高亮、自动意图路由和语义检索仍未实现。

#### 第二轮增加

- 增加 `SearchSuggestionService` 实现，明确最小触发字符数、防抖、候选数量和历史词/热门词来源。
- 保存真实查询词及期望前几名结果，建立零结果率、点击率、延迟和相关度评估基线。
- 数据量或相关度要求超过 MySQL `LIKE` 后，再接 Elasticsearch/OpenSearch；MySQL 保持真相源，索引可全量重建。
- 搜索引擎接入后增加增量同步、失败重试、全量重建、索引别名切换、超时和降级。
- 关键词检索稳定后再增加向量召回和重排，以混合检索保留精确名称与结构化过滤能力。
- 深分页改为 `search_after`/游标，不无限增大页码偏移。

### 2.5 博客、图片与点赞域

#### 第一轮保留

- 发布博客：校验商户、标题、正文和图片，写入 `tb_blog`。
- 查询博客：详情、热门列表、作者列表和 Feed 列表。
- 编辑博客：只允许作者修改商户、标题、正文和图片。
- 删除博客：只允许作者删除，并清理点赞、评论和图片关系。
- 点赞：维护 `tb_blog_like` 关系和 `tb_blog.liked` 总数。
- 点赞用户列表：查询点赞关系，再查询对应用户资料并返回。
- 发布必须有合法店铺、标题、正文和图片，作者取自当前登录用户。
- 编辑和删除只能由博客作者发起。
- 点赞时新增关系并增加计数，取消点赞时删除关系并减少计数。
- 详情返回正文，列表返回博客卡片。

#### 第二轮增加

- 发布、编辑、删除的多表数据库事务。
- 点赞关系与点赞计数的数据库事务。
- `UNIQUE(blog_id, user_id)` 点赞唯一约束。
- 编辑字段白名单 UPDATE。
- 编辑和删除的博客行锁、图片条件更新。
- 发布 `clientRequestId` 幂等记录。
- 图片 `TEMP/BOUND/DELETING` 状态、提交后删除和定时重试。
- 博客列表批量装配、复合游标和 Feed 快照。

### 2.6 社交关系域

#### 第一轮保留

- 关注和取关：操作 `tb_follow`。
- 是否关注：按 `(user_id, follow_user_id)` 查询 MySQL。
- 关注列表：查询 `tb_follow` 后查询用户资料。
- 共同关注：在 MySQL 对两份关注关系求交集。
- Following Feed：先查关注 ID，再按作者集合查询博客。
- 禁止关注自己。

#### 第二轮增加

- `UNIQUE(user_id, follow_user_id)` 关注唯一约束。
- 关注和取关的目标状态幂等语义。
- 目标用户存在性校验。
- 数据库提交后的 Redis Set 同步。
- Caffeine 关注缓存和 Feed 快照失效。
- 共同关注缓存完整性标记与 MySQL 回源。

### 2.7 Feed 与推荐域

#### 第一轮保留

```text
查询当前用户关注列表
  → 一次 SQL 查询这些作者的博客
  → 按发布时间倒序
  → 补充作者和点赞状态
  → 返回列表
```

- Following Pull Feed。
- 按关注作者召回博客。
- 按发布时间倒序。
- 返回作者与点赞状态。

#### 第二轮增加

- 作者与点赞状态批量装配。
- opaque 复合游标和稳定分页。
- Following、For You 产品模式。
- 多路召回、加权排序和作者打散。
- Redis List 版本化快照。
- 曝光去重、Redis 降级和缓存失效。

### 2.8 优惠券、秒杀与评论域

#### 2.8.1 当前完成度与 `hmdp-plus` 对照

| 功能 | 当前 `hmdp` | `hmdp-plus` | 判定 |
|---|---|---|---|
| 查询店铺优惠券 | 已实现 `GET /voucher/list/{shopId}` | 已实现 | 当前已完成 |
| 新增普通券 | 已实现 `POST /voucher` | 已实现 | 当前已完成，管理权限和输入边界仍待收口 |
| 新增秒杀券 | 已实现 `POST /voucher/seckill`，写入券基础信息和秒杀配置 | 已实现，并同步 Redis 库存和活动缓存 | 当前基础创建已完成 |
| 查询、修改秒杀券及调整库存 | 未实现 | 已实现查询详情、修改配置和调整库存 | 第一轮管理闭环缺失 |
| 秒杀下单 | Controller 固定返回“功能未完成”，Service 为空 | 已实现访问令牌、Redis Lua 资格判断、Kafka 异步下单 | 第一轮核心交易缺失 |
| 查询抢券结果与取消领取 | 未实现 | 已实现按订单 ID 轮询、按券查询本人订单和取消领取 | 第一轮订单闭环缺失 |
| 售罄订阅与到券提醒 | 未实现 | 已实现订阅、取消订阅、批量状态和延时提醒 | Plus 扩展能力 |
| 博客评论 | 已实现创建、回复、游标分页、作者删除和事务计数，Nuxt 详情页已接入 | Controller、Service 仍为空 | 当前 hmdp 第一轮闭环已完成 |
| 店铺评价 | 没有表、Entity、Controller 或 Service，页面是三条静态模板 | 页面同样是静态模板 | 两个项目都未开始 |

完成度结论：当前优惠券域完成“展示 + 创建”；秒杀域只有活动配置，没有抢券订单；博客评论已形成真实前后端基础闭环，店铺评价仍没有真实链路。`hmdp-plus` 可用于参考秒杀进阶实现，不能作为评论域的完成范例。

#### 2.8.2 优惠券管理

##### 第一轮保留

- 用户打开店铺详情页，查询该店普通券和秒杀券。
- 运营人员新增普通券和秒杀券。
- 运营人员按券 ID 查询详情，修改标题、规则、金额、活动时间、状态和库存。
- 管理写接口校验管理员身份、店铺存在、金额为正、库存非负以及开始时间早于结束时间。
- 列表只返回当前店铺可展示的券，并携带秒杀库存和活动时间。

##### 第二轮增加

- 新增秒杀券时 `tb_voucher` 与 `tb_seckill_voucher` 的数据库事务。
- 更新券配置与库存时的影响行数裁决、并发版本控制和合法状态迁移。
- 管理请求 DTO、字段白名单和操作审计。
- 券列表、券详情与 Redis 库存缓存的提交后失效或重建。
- 活动发布、修改和下架后的缓存同步、定时预热和失败重试。

#### 2.8.3 秒杀下单

##### 第一轮保留

- 已登录用户在店铺详情页点击“限时抢购”。
- Service 根据券 ID 查询秒杀配置，校验券已上架、活动已开始、活动未结束且库存充足。
- Service 查询当前用户是否已经参加过该券活动，执行一人一单业务规则。
- Service 依次扣减 MySQL 库存、创建 `tb_voucher_order` 并返回订单 ID。
- 用户按订单 ID 查询抢券结果，或按券 ID 查询自己的订单及其状态。
- 用户取消未使用的订单，订单变为已取消并恢复一张库存。
- 第一轮规则定义为同一用户在同一活动中最多创建一张订单；取消释放库存，但不产生第二张订单。

```text
用户点击“限时抢购”
  → POST /voucher-order/seckill/{voucherId}
  → 查询券状态、活动时间和库存
  → 查询本人是否参加过该活动
  → 扣减一张库存
  → 创建订单
  → 返回 orderId
```

##### 第二轮增加

- 库存扣减与订单创建的数据库事务。
- `UPDATE ... SET stock = stock - 1 WHERE stock > 0` 条件扣减，防止并发超卖。
- `UNIQUE(user_id, voucher_id)` 最终保证一人一单，并把重复请求对齐到同一订单结果。
- 产品若允许取消后重新领取，则显式增加领取轮次或独立资格记录，不能直接移除最终唯一性保护。
- 稳定请求 ID、订单 ID 和幂等结果，处理双击、重试与响应丢失。
- 入口限流、秒杀访问令牌和 Redis Lua 原子校验时间、状态、库存与购买资格。
- Kafka 异步创建订单、明确“已受理/已创建”状态，并由查询接口轮询最终结果。
- 消息投递确认、消费者幂等、重试、死信、Redis 回滚、数据库补偿和库存对账。
- 取消订单时可靠同步数据库状态、MySQL 库存和 Redis 库存；购买资格按活动规则保持已使用或恢复。
- 售罄订阅、自动发券、延时提醒、监控指标和容量压测。

#### 2.8.4 博客评论

##### 第一轮保留

- 已登录用户在博客详情页发布一级评论。
- 已登录用户回复一级评论或指定回复对象，使用 `parentId` 和 `answerId` 表达关系。
- 用户按博客 ID 分页查看正常状态评论，返回评论内容、作者摘要、发布时间和回复关系。
- 评论作者删除自己的评论。
- 创建和删除评论时依次维护 `tb_blog_comments` 与 `tb_blog.comments` 数量。

##### 第二轮增加

- 当前已具备评论与计数同事务、评论树归属校验、作者权限、opaque 游标和批量作者装配；后续用真实 MySQL 补事务回滚、并发删除和计数对账测试。
- 父评论改用明确的软删除/占位语义，避免删除一级评论时直接移除有价值的回复上下文。
- 为 `(blog_id, status, parent_id, create_time, id)` 增加匹配索引并验证执行计划。
- 增加频率限制、敏感内容审核、举报和封禁状态流转。
- 评论列表缓存、评论数缓存与数据库提交后的同步失效。

#### 2.8.5 店铺评价

##### 第一轮保留

- 已登录用户为店铺提交评分、文字和图片评价。
- 用户按店铺 ID 分页查看评价，返回评价人摘要、评分、内容、图片和时间。
- 评价作者删除自己的评价。
- 创建和删除评价时依次维护店铺评价数与平均评分。
- 店铺评价使用独立数据模型，不复用只含 `blog_id` 的 `tb_blog_comments`。

##### 第二轮增加

- 评价记录、图片绑定、店铺评价数和平均分修改的数据库事务。

## 三、第二轮：数据库故障、回滚与并发处理

### 3.1 当前已经实现的数据库保护

| 业务 | 当前机制 | 解决的问题 | 代码位置 |
| --- | --- | --- | --- |
| 博客发布 | `@Transactional` | 博客、图片绑定和幂等结果不会只成功一半 | `service/blog/BlogCommandService.publish()` |
| 博客编辑/删除 | 行锁 + 事务 + 条件更新 | 并发编辑不会互相覆盖，失败时关系修改一起回滚 | `BlogCommandService.update()/delete()` |
| 博客编辑字段 | 字段白名单 UPDATE | 请求不能覆盖作者、点赞数、评论数等服务端维护字段 | `mapper/BlogMapper.updateEditableFields()` |
| 点赞/取消点赞 | 关系和计数同事务 | 不出现关系成功但计数没变，或计数变化但关系失败 | `service/blog/BlogLikeService` |
| 关注/取关 | 事务内写 MySQL，提交后同步缓存 | 数据库回滚时不提前污染 Redis | `service/impl/FollowServiceImpl`、`service/follow/FollowChangedEventListener` |
| 新增秒杀券 | 两表同事务 | `tb_voucher` 和 `tb_seckill_voucher` 一起成功或回滚 | `service/impl/VoucherServiceImpl` |
| 重复发布 | 独立幂等记录、唯一键、行锁、请求指纹 | 双击和响应丢失重试不会重复创建博客 | `service/blog/BlogIdempotencyService` |
| 重复关注 | 联合唯一键 + 幂等 SQL | 并发关注最终只有一条关系 | `mapper/FollowMapper`、V5 迁移 |
| 重复点赞 | 联合唯一键 + 只处理唯一键冲突 | 并发 PUT 只增加一次计数，其他数据库异常继续失败 | `mapper/BlogLikeMapper`、V2 迁移 |
| 图片并发绑定 | 带旧状态条件的 UPDATE | 只有仍处于预期状态的图片才能被绑定、替换或领取删除 | `service/impl/BlogImageServiceImpl` |

这里的核心规则是：**只要希望数据库回滚，就不能在 Service 中把未知数据库异常吞掉并返回成功。** 当前点赞只捕获明确的 `DuplicateKeyException`，其他异常继续抛出，事务才能正确回滚。

### 3.2 当前仍存在的数据库与回滚缺口

| 模块 | 当前缺口 | 可能结果 | 第二轮建议 |
| --- | --- | --- | --- |
| 用户注册 | 账号创建与可选手机号绑定不在同一事务 | 用户已创建，但绑定失败；重试又提示账号存在 | 要么同事务完成，要么设计明确的两阶段注册状态和一次性凭证 |
| 用户资料初始化 | 登录时创建 `tb_user_info` 失败只记录日志 | Token 已签发，但资料行可能长期缺失 | 将资料初始化并入注册事务，或提供可靠的补建任务 |
| 关注目标 | 没有外键，也没有验证目标用户存在 | 可以插入指向不存在用户的关注关系 | 写入前校验目标用户，或评估增加外键 |
| 共同关注 | 直接对可能未完整加载的 Redis Set 做 `SINTER` | MySQL 有共同关注，接口却返回空 | 基础版改用 MySQL 自连接；需要缓存时增加完整装载标记与回源 |
| 是否关注 | Redis 命中 true 时不回查 MySQL | 取关后的 Redis 删除失败会长期误报已关注 | 直接查唯一索引，或使用有版本、可重建的完整缓存 |
| 店铺更新 | 忽略 `updateById()` 返回值 | 店铺不存在或更新 0 行仍返回成功 | 检查影响行数并返回 404/冲突 |
| 店铺删除 | 忽略删除结果，且不清理缓存和 GEO | 已删除店铺仍可能从缓存或附近列表出现 | 检查影响行数，并同步处理 Cache/GEO |
| 临时图片删除 | 先删文件再删数据库；数据库删除失败时恢复 TEMP | 数据库行恢复了，但文件已经不存在 | 删除后保留 DELETING 状态并重试元数据删除，不应恢复为 TEMP |
| 上传补偿 | 文件写入成功、资产记录写入失败后只尽力删文件 | 补偿删除也失败时产生无数据库记录的孤儿文件 | 增加存储清单对账或临时命名空间生命周期规则 |
| 点赞计数 | `tb_blog.liked` 是关系表的冗余计数，无定期对账 | 非正常写入或历史故障可能让关系数和计数漂移 | 增加离线校验/修复任务，或定期按关系表重算 |
| 秒杀订单 | 功能未实现，订单表无一人一单唯一键 | 实现后若只先查再写，会并发重复下单或超卖 | 第二轮增加唯一键、条件扣库存和订单事务 |
| 定时任务 | 清理任务外层没有统一异常捕获和指标 | 一次数据库异常只能看到调度日志，无法观测连续失败 | 增加失败计数、告警和下次重试可见性 |

### 3.3 数据库异常应该怎样分层

推荐按三层处理，不要把检测和业务揉在一个大函数里：

1. **Mapper/数据库层裁决。** 唯一键、条件 UPDATE、行锁和事务负责最终数据正确性。
2. **Service 只处理可预期业务结果。** 例如唯一键表示“已经点赞”，影响 0 行表示“状态已改变”；未知 `DataAccessException` 不吞掉。
3. **全局异常层统一输出。** `WebExceptionAdvice` 隐藏 SQL 和堆栈，只返回稳定错误码和 `traceId`。

当前全局异常层会把所有未知 `RuntimeException` 统一返回 500。第二轮可以进一步区分：

- 数据库暂时不可用：`503 SERVICE_UNAVAILABLE`。
- 死锁或锁等待超时：仅对幂等请求做有界重试。
- 唯一约束冲突：只有业务明确知道该唯一键语义时才转成 409 或幂等成功。
- 参数和业务冲突：400/404/409，不伪装成数据库故障。

## 四、第二轮：网络与外部资源异常处理

这里的“网络问题”不只指浏览器断网，还包括应用访问 Redis、短信平台、对象存储时的超时、连接断开和响应丢失。

### 4.1 先按依赖职责分类

| 类型 | 项目中的例子 | 故障时原则 |
| --- | --- | --- |
| 业务真相 | MySQL 用户、博客、关注、点赞、订单 | 不能假装成功；事务回滚并明确失败 |
| 安全关键依赖 | Redis Token、验证码 | 故障时 fail-closed，不能绕过登录；应返回 503 而不是放行 |
| 可重建缓存 | 店铺缓存、Feed 快照、关注缓存 | 故障时回源 MySQL，不能把缓存结果当业务真相 |
| 辅助体验 | Feed 曝光去重、限流统计 | 可以 fail-open，但必须记录告警和指标 |
| 外部副作用 | 短信、文件/对象存储、未来 MQ | 需要超时、幂等、状态记录和补偿，数据库事务不能回滚它们 |

### 4.2 当前已经实现的网络/外部资源处理

| 场景 | 当前处理 | 效果 |
| --- | --- | --- |
| Feed 快照 Redis 失败 | 捕获异常并重新从召回链路读取 | Redis 故障不会直接让 Feed 失败 |
| Feed 曝光 Redis 失败 | 读取失败不过滤，写入失败跳过 | 最坏只是偶尔重复推荐 |
| 博客限流 Redis 失败 | 记录告警并临时放行 | 限流故障不升级为博客接口全站故障 |
| 关注提交后 Redis 同步失败 | MySQL 已提交，缓存失败只记日志 | 数据库真相不会被 Redis 异常回滚 |
| 短信发送失败 | 释放发送锁并返回失败 | 用户可以稍后重新请求验证码 |
| 博客上传写数据库失败 | 尝试删除刚写入的文件 | 减少孤儿文件 |
| 已绑定图片删除失败 | 保留 `DELETING`、记录错误并定时重试 | MySQL 提交后文件暂时删不掉仍可恢复 |
| 点赞响应丢失 | PUT/DELETE 表达目标状态，前端失败后 GET 详情对齐 | 重试不会把点赞反转，前端不猜计数 |
| 发布响应丢失 | 前端复用 `clientRequestId` 和冻结 payload | 同一请求重试返回第一次博客 ID |

### 4.3 当前仍存在的网络与跨资源缺口

| 模块 | 故障窗口 | 当前可能结果 | 第二轮建议 |
| --- | --- | --- | --- |
| 验证码发送 | 短信已发送，随后 Redis 保存验证码失败 | 用户收到一个服务端无法验证的验证码 | 先可靠保存待发送验证码，再调用短信；失败时使记录失效并允许重发 |
| 注册登录 | MySQL 已创建用户，Redis Token 写入失败 | 接口返回失败，但账号已经存在；手机号验证码还可能已删除 | 将注册结果与登录结果分开；重试注册时能够识别并继续签发 Token |
| Token 写入 | Redis Hash 写入成功，`EXPIRE` 失败 | 留下永久有效 Token | 用 Lua/事务一次写值和 TTL，失败时删除半成品 |
| Token 解析 | Redis 连接异常未分类处理 | 受保护接口直接进入通用 500 | 安全上继续拒绝访问，但返回明确 503 并记录认证依赖告警 |
| 登出 | Redis 删除失败 | 客户端认为失败，旧 Token 仍有效 | 返回明确失败并支持重试；生产可增加 Token 版本/吊销记录 |
| 签到 | 签到数据只存在 Redis | Redis 数据丢失就没有权威记录 | 明确它是可丢失活动数据，或增加持久化/备份方案 |
| 关注缓存 | MySQL 提交后进程崩溃，事件未执行 | Redis Set、Caffeine、Feed 指针可能不一致 | 当前规模先让关系查询回源 MySQL；生产化再上 Outbox/CDC |
| Caffeine | 多实例只失效当前 JVM | 其他实例最多读取 5 分钟旧关注列表 | 缩短 TTL、广播失效，或取消该层直到确有性能收益 |
| 店铺查询 | Redis 或分布式锁不可用 | 当前不会可靠回源，查询可能直接失败 | Redis 异常直接查 MySQL；锁等待改为有界循环而非递归 |
| 店铺更新 | MySQL 成功后删除缓存失败 | 返回 500 且旧缓存继续存在 | 数据库成功仍返回明确结果，同时记录缓存失效任务或采用延迟双删/事件 |
| GEO 预热 | 启动期间 Redis 连接失败 | `@PostConstruct` 可能阻止应用启动 | 将预热改为可重试后台任务；普通店铺查询不依赖 GEO 成功 |
| 本地文件 | 数据库提交后进程崩溃或文件系统不可用 | 文件和资产状态短暂不一致 | 已有 DELETING 重试；多实例时升级为 Outbox + 对象存储清单对账 |
| 前端普通请求 | 多数静态 Axios 请求无统一超时 | 请求可能长时间 pending，用户不知道能否重试 | 统一超时、错误分类和 loading 释放；只自动重试安全 GET |
| Nuxt API | 明确 `retry: 0`，但未统一超时 | 避免误重放写请求，但慢连接缺少上限 | GET 可有界重试；写请求用幂等键后才允许重试；统一 Abort timeout |

### 4.4 响应丢失和请求失败不是一回事

客户端看到“网络失败”时，服务端可能有三种状态：

```text
A. 请求根本没到服务端
B. 服务端执行到一半并回滚
C. 服务端已经提交成功，只是响应丢了
```

因此不能看到网络错误就简单再执行一次非幂等 POST。项目中目前有两种正确示例：

- 点赞使用目标状态 PUT/DELETE；重复请求结果不变。
- 发布使用 `clientRequestId`；同一次重试返回第一次结果。

后续下单、发送消息和管理端创建资源也应采用同样原则：客户端携带稳定请求 ID，数据库唯一约束负责最终裁决，服务端重放第一次结果。

### 4.5 店铺查询的缓存与故障增强

第一轮已经能从 MySQL 正确返回店铺详情或“不存在”。第二轮才在这条正确基线上增加缓存，目标是减少热点详情查询、阻止相同无效 ID 反复访问数据库，并保证 Redis 故障时基础查询仍可用。

#### 4.5.1 正常店铺的 Cache Aside

```text
GET /shop/{id}
  → 查询 cache:shop:{id}
  ├─ 命中店铺 JSON：直接返回
  └─ 未命中：查询 MySQL
       ├─ 店铺存在：缓存 JSON 30 分钟并返回
       └─ 店铺不存在：进入空值缓存分支
```

现实触发仍然是用户点击店铺、打开分享链接或从博客查看关联商户；缓存只是后端加速方式，不改变产品动作和接口语义。

#### 4.5.2 不存在店铺的空值缓存

```text
第一次请求 GET /shop/7
  → Redis 没有 Key
  → MySQL 确认店铺 7 不存在
  → cache:shop:7 写入空字符串，TTL 2 分钟

2 分钟内再次请求 GET /shop/7
  → Redis 命中空字符串
  → 直接返回 404，不再查询 MySQL
```

店铺 7 可能曾经存在但已经删除，旧收藏、分享链接或浏览器历史仍可能继续访问；也可能来自过期列表、爬虫或人为构造 URL。空值缓存防的是**同一个无效 ID 被高频重复请求**形成缓存穿透，不是正常页面主动查找不存在的店铺。

空值缓存的能力边界：

- 攻击者不断更换随机 ID 时，每个新 ID 仍会第一次访问 MySQL；需要参数校验、接口限流，规模足够大时再评估布隆过滤器。
- 空值 TTL 必须短于正常店铺缓存，避免店铺随后被创建或恢复后长期显示不存在。
- 返回结果仍应是 404/稳定错误码，不能因为 Redis 存的是空字符串就返回普通成功。

#### 4.5.3 热点失效与有界互斥重建

同一热门店铺缓存到期时，大量请求可能同时回源。第二轮可让一个请求取得 `lock:shop:{id}` 并重建缓存，其余请求短暂等待后重查缓存，但必须具备：

- 最大重试次数或总等待超时，不能无限递归。
- 线程中断后立即结束，不继续占用请求线程。
- 解锁失败单独记录，不能覆盖已经成功得到的店铺结果。
- 锁只是减少重复回源；MySQL 仍是最终数据来源。

#### 4.5.4 Redis 故障回源

`cache:shop:{id}` 是可重建缓存，不是店铺真相。Redis `GET`、加锁或写缓存失败时，应记录告警并直接查询 MySQL：

```text
Redis 正常 → 按 Cache Aside 查询
Redis 异常 → 跳过缓存和分布式锁 → 查询 MySQL → 返回真实结果
```

回源可以保证功能可用，但 Redis 长时间故障会让流量集中到 MySQL，因此还需要数据库连接池保护、超时、限流和监控，不能把“可以回源”理解成无限承载。

#### 4.5.5 店铺写入后的缓存和 GEO 一致性

一旦第二轮启用店铺缓存，写操作必须同步维护派生数据：

| 写操作 | 必须处理 |
|---|---|
| 新增店铺 | 清除可能存在的同 ID 空值缓存；有坐标时写入对应 `shop:geo:{typeId}` |
| 更新普通资料 | MySQL 成功后删除 `cache:shop:{id}`，下次读取重建 |
| 更新类型或坐标 | 删除详情缓存，并从旧 GEO Key 移除、向新 GEO Key 写入 |
| 删除店铺 | 删除详情缓存和 GEO member，旧链接随后返回不存在 |

这里要区分两种失败：MySQL 写失败时业务失败并保持旧缓存；MySQL 已成功但 Redis 同步失败时，数据库结果不能被回滚成失败前状态，应记录可重试的缓存失效任务或事件。当前项目尚未实现可靠任务，因此这仍是第二轮缺口。

| `sms` | 短信发送抽象 | 生产实现需超时、供应商错误分类和敏感日志脱敏 |
| `frontend` | 请求状态与服务端结果展示 | 写请求禁重复点击、结果未知时回源、只重试幂等请求 |

## 六、推荐的实际学习与改造顺序

### 第一轮：先把业务主线讲清楚

1. 画出各域正常流程，只追踪 Controller、Service、Mapper、MySQL/Redis。
2. 店铺详情先实现“页面自动传 ID → MySQL 查询 → 存在返回详情/不存在返回 404”，不先混入空值缓存和分布式锁。
3. 搜索先保持 `SearchController → ShopSearchService → MySQL` 基线，确认接口、DTO 和查询样本，再决定何时接搜索引擎。
4. 共同关注先改成 MySQL 查询，避免在基础版引入“不完整 Redis Set”。
5. 评论第一轮已经实现；秒杀下单按当前需求继续保持未实现，真正开始交易轮次时先画正常流程，再单独进入第二轮增加并发与事务保护。
6. 为基础流程补 Service 单元测试，先覆盖成功、参数错误、资源不存在和权限错误。

### 第二轮 A：数据库正确性

1. 回到博客发布、编辑、删除和点赞流程，逐个制造“第二步失败”，再解释当前事务为什么能让前面步骤回滚。
2. 对同一博客点赞和同一用户关注制造并发重复请求，再解释联合唯一索引为什么是最终裁决者。
3. 对博客编辑提交额外服务端字段，验证字段白名单 UPDATE 不会覆盖作者和计数。
4. 补用户注册与手机号绑定的事务或两阶段状态机。
5. 补秒杀库存条件更新和一人一单唯一约束。
6. 检查所有 `save/update/remove` 的影响行数。
7. 通过真实 MySQL 集成测试验证事务、唯一键和 Flyway；引入 Testcontainers 需要先取得新增依赖授权。

### 第二轮 B：网络结果不确定

1. 给发布、下单等创建命令定义幂等键。
2. 前端区分“服务端明确拒绝”和“没有收到响应”。
3. 只对 GET 或具有幂等键的写请求做有界重试。
4. 为 Redis、短信和文件存储定义超时；失败返回稳定错误码。
5. 为店铺详情增加正常值/空值缓存、有界互斥重建和 Redis 故障回源；更新或删除后同步失效详情缓存与 GEO。
6. 接入远程搜索引擎后，定义查询超时、可接受的 MySQL 降级范围，以及索引延迟或集群不可用时的错误语义。

### 第二轮 C：跨资源最终一致

1. 先保留现有 after-commit 和图片补偿任务。
2. 增加失败指标、重试次数和对账工具。
3. 只有进入多实例或高可靠阶段后，再把进程内事件升级为 Outbox/CDC/MQ。

## 七、故障测试清单

| 注入故障 | 应验证的结果 |
| --- | --- |
| 发布时图片绑定 SQL 失败 | 博客和幂等成功状态都不提交 |
| 点赞关系插入后计数更新失败 | 点赞关系回滚，计数不变 |
| 关注事务回滚 | Redis Set 和 Feed 指针不更新 |
| MySQL 提交后 Redis 断开 | MySQL 结果仍正确，缓存可回源或等待重建 |
| Redis 在认证时断开 | 不能绕过登录，应返回明确依赖不可用 |
| 短信发送成功后 Redis 写入失败 | 不能让用户拿到永远无法使用的验证码 |
| 文件删除成功后数据库删除失败 | 元数据保持可重试状态，不能恢复成“文件仍存在” |
| 发布成功但 HTTP 响应丢失 | 相同 `clientRequestId` 重试不创建第二篇博客 |
| 点赞成功但 HTTP 响应丢失 | 重复 PUT 仍保持已点赞，GET 可对齐最终状态 |
| 两个请求同时抢最后一份库存 | 只能一个订单成功，库存不能小于 0 |
| 重复访问同一个不存在的店铺 ID | 第一次查 MySQL 后写短 TTL 空值，后续请求直接返回不存在 |
| 不断请求不同的随机店铺 ID | 参数校验和限流生效，不能把空值缓存当作完整防护 |
| 店铺详情查询期间 Redis 断开 | 回源 MySQL 并返回真实店铺或不存在，不因缓存故障直接失败 |
| 店铺更新成功但缓存删除失败 | MySQL 新值保持成功，并留下可观测、可重试的缓存失效记录 |

## 八、设计要点

1. **第一轮只讲理想条件下的业务顺序；事务、唯一约束、锁、幂等和失败补偿全部在第二轮解释。** 这是学习分层，不要求从当前代码中删除已经生效的保护。
2. **MySQL 保存业务真相，Redis 缓存必须允许丢失和重建。** 唯独认证、验证码和签到当前本身依赖 Redis，应明确它们是关键状态而不是普通缓存。
3. **数据库事务只能回滚数据库，不能回滚 Redis、短信和文件。** 跨资源操作需要 after-commit、状态机、重试或 Outbox。
4. **只处理能够准确识别的异常。** 重复键可以映射为幂等结果，未知数据库异常必须继续失败并触发回滚。
5. **网络失败代表结果未知。** 写请求是否能安全重试，取决于接口是否幂等，而不是前端是否愿意再点一次。
6. **降级策略由依赖职责决定。** Feed 曝光和限流可以 fail-open，认证不能 fail-open，业务写入不能假装成功。
7. **先讲清最小正常流程，再按真实故障和压测证据增加复杂度。** 当前阶段不需要为了“工业级”立即引入微服务、MQ 或分布式事务。
8. **“资源不存在”属于第一轮业务结果，“为空结果做短 TTL 缓存”属于第二轮性能防护。** 两者不能揉成一个无法解释现实触发的步骤。
9. **搜索是独立读取能力，不是店铺 CRUD 的附属方法。** Controller 固定协议，每种内容使用独立 Search Service，底层 MySQL 或搜索引擎只是可替换实现。
